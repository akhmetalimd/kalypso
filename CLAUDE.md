# KALYPSO — правила проекта

KALYPSO (KAzakhstan LYmphoma Patients Survival and Outcomes) — пробная платформа
регистра лимфопролиферативных заболеваний. Требования — PRD v1.0 (у владельца проекта).

**Текущий фокус — только основная платформа:** ручной ввод (модули ХЛЛ и ДВКЛ), карточка,
роли, аудит, полнота, дашборды, «Исследователь выживаемости», документы по шаблонам.
Интеграция с his.kz и AI-ассист **убраны** (решение владельца проекта, 2026-10-19): ими
займутся программисты позже. Их прежняя реализация — в истории git, коммит `fe28537`
(П2: AI-ассист и сверка; П4: коннектор МИС). Не возвращать без явной просьбы.

## Непреложные правила

1. **Только синтетика.** В репозитории, тестах, фикстурах, логах и примерах — только
   синтетические данные. Реальные данные пациентов не загружаются до соглашения об
   обработке данных и одобрения этического комитета.
2. **ИИН хранится открыто, без шифрования** (решение владельца проекта на раннем этапе):
   колонка `patient.iin` — 12 цифр, уникальная, контрольная цифра проверяется
   `kalypso/deid.normalize_iin`. По ИИН — дедупликация между филиалами.
   С открытым ИИН регистр — база персональных данных: см. правило 1.
3. **Кто видит ИИН.** В интерфейсе — только роли с правом `patient.iin` (врач своего
   филиала, куратор). ИИН **не попадает** в выгрузку, аналитику и дашборды, журнал аудита
   (значение маскируется `***`), логи, сообщения об ошибках и URL (поиск — только POST).
4. **Свободный текст без идентификаторов.** Гистология и ПЭТ-КТ проверяются перед
   сохранением (`find_identifiers`); БД дополнительно отвергает 12-значные числа в этих полях.
5. **Без жёсткого удаления.** Клинические записи удаляются мягко (`deleted_at`);
   роль приложения не имеет DELETE на клинических таблицах.
6. **Два рубежа доступа.** Права проверяют сервисы (`config/roles.json`), и то же
   самое повторяет RLS в БД (миграция 0004). Новая клиническая таблица с `patient_id`
   получает такие же политики; функции, которым нужно видеть всё (проверки, дедупликация),
   — SECURITY DEFINER и отдают минимум.
7. **Аудит — на триггерах БД.** Приложение в каждой транзакции делает
   `SET LOCAL app.user_id = '<uuid>'` (и `app.change_reason` при пересмотре диагноза).
   `audit_log` и `diagnosis_version` неизменяемы.

## Аналитика

- Конечные точки — `registry_core.endpoint` (OS, TTFT, PFS, mPFS, EFS, TTNT): определения в
  `registry_core.ENDPOINTS`; неточные даты — середина периода (`impute_date`); TTFT: смерть без
  лечения — цензура. События в день старта линии исходом линии не считаются.
- Каплан–Майер — `registry_core.km_estimate` (Гринвуд, ДИ log-log, ДИ медианы). Проверен на
  наборе Freireich 6-MP. **p-value, log-rank, Cox в платформе не считаются** — только на выгрузке.
- Группирующий маркер/анализ — только измеренный не позже 90 дней после начала отсчёта
  (`kalypso/analytics.py`), иначе «не определено на старте». Порог показателя — внешний.
- Нозологии не смешиваются: группировка нозологии сужает когорту до неё (`analytics.GROUPING_SETS`).
- Признак, появляющийся после начала отсчёта (Deauville после 1-й линии), — только анализом от
  ориентира (landmark): отсчёт от даты ПЭТ-КТ, события и цензура до неё — вне анализа.
- Графики — `kalypso/charts.py`, SVG на сервере; цвета только классами `.s1….s6` и переменными
  `--series-N` (палитра навыка dataviz, проверена валидатором на фонах карточек). У каждого
  графика — табличный двойник. Больше 6 серий — сворачивать в «прочие».
- Документы (FR-8) — `kalypso/docgen.py`, шаблоны из данных регистра, без AI, с пометкой «черновик».

## Схема данных

- `schema.sql` — нормативный baseline, **не редактируется**. Изменения — файлами в
  `db/migrations/` (порядковый номер + суть). Применение: `psql -1 -f <файл>`.
  Пока платформа нигде не развёрнута, миграции 0002–0004 приведены к чистому виду;
  0005 — проверки модуля ДВКЛ (стадия Lugano, IPI, ответ Lugano 2014 и Deauville);
  0006 — чтение `schema_migrations` для `check`. Миграции не должны требовать суперпользователя:
  их применяет владелец схемы (`tests/test_deploy.py` репетирует это на чистом кластере).
- В БД хранятся **коды**, а не русские подписи (`alive`, `death`, `M`…). Подписи на
  русском/казахском — в слое локализации. Названия систем и критериев (`Rai`, `Binet`,
  `iwCLL 2018`) остаются как есть.
- Провенанс у каждой записи: `source` (сейчас только `manual`; другие источники добавляются
  `ALTER TYPE record_source ADD VALUE`) + `provenance` (`retrospective` / `prospective`).
- Пропуск «условного» поля — код пропуска (`patient_missing`, `module_data.missing`),
  а не пустая ячейка.
- Нозологии — дерево WHO-HAEM5 в `config/nosology_tree.json`; модульные поля — EAV
  (`module_data`), без ALTER TABLE на каждую нозологию. Всё нозолого-специфичное (системы и
  значения стадий, индекс, критерии ответа, поля модуля, подсказки режимов) — в узле дерева и
  читается через `registry.profile()`; новая нозология = узел + проверки БД миграцией + тесты.
- Индексы: ручной индекс карточки (`index_name/score/group`, группа выводится из балла,
  `registry_core.INDEXES`) сверяется с расчётом по данным (`registry.computed_indices`):
  ХЛЛ — CLL-IPI; ДВКЛ — IPI (в карточке), R-IPI и NCCN-IPI (только расчёт). ЛДГ для IPI —
  категория относительно ВГН лаборатории (поле модуля), а не значение анализа.
- Ответ — по критериям нозологии (`registry_core.RESPONSES`, `check_response`): ХЛЛ — iwCLL 2018;
  ДВКЛ — Lugano 2014 (по ПЭТ-КТ — CMR/PMR/NMR/PMD с Deauville, CMR — 1–3, иначе 4–5).

## Движок

- `registry_core.py` — без внешних зависимостей; логика, одинаковая на любой платформе.
  Самотест: `python registry_core.py`. Менять сигнатуры существующих функций нельзя,
  только добавлять новые.

## Устройство

- `kalypso/deid.py` — проверка ИИН (формат, контрольная цифра, дата), поиск идентификаторов в тексте.
- `kalypso/registry.py` — доменные сервисы: **единственный путь записи** в регистр
  (права, приведение ввода, проверки registry_core, одна транзакция, предупреждения QC).
- `kalypso/auth.py`, `kalypso/rbac.py` + `config/roles.json` — вход, сессии, CSRF, роли.
- `kalypso/admin.py`, `kalypso/export.py` — пользователи/филиалы/аудит/запросы, деидент. выгрузка.
- `kalypso/analytics.py`, `kalypso/charts.py`, `kalypso/docgen.py` — аналитика, графики, документы.
- `kalypso/web/` — FastAPI + Jinja2, без JS.
- `kalypso/locales/*.json` — подписи кодов (ru; kk — заготовка).
- `kalypso/migrate.py` — `schema.sql` + `db/migrations/*.sql`, учёт в `schema_migrations`.
- `kalypso/synthetic.py` — синтетические когорты ХЛЛ и ДВКЛ через те же сервисы.
- `kalypso/cli.py` + `kalypso/ops.py` — эксплуатация: `migrate`, `check` (роль входа не обходит RLS,
  миграции применены), `serve`, `create-admin`, `seed-synthetic` (только пустой регистр).
- `kalypso/logsafe.py` — фильтр журналов: любое 12-значное число -> `***` (на всех обработчиках сервера).
- `deploy/` — Docker Compose (PostgreSQL 16 + приложение + nginx/HTTPS), первичные роли БД,
  резервные копии; инструкция для ИТ — `docs/deploy.md`. Роли: `kalypso_owner` — владелец схемы
  (миграции), `kalypso_web` — логин приложения в роли `kalypso_app`.

## Запуск и тесты

```bash
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements-dev.txt
.venv/Scripts/python -X utf8 -m kalypso.dev      # http://127.0.0.1:8765, учётки — kalypso/dev_seed.json
.venv/Scripts/python -X utf8 -m pytest
```

- `python -m kalypso.dev` поднимает встроенный PostgreSQL в `.devdb/`, применяет миграции и
  при пустой БД создаёт филиалы, пользователей и 200 синтетических пациентов ХЛЛ; если нет
  пациентов ДВКЛ — добавляет 100 синтетических пациентов ДВКЛ.
  Удалить `.devdb/` — начать с чистой БД.
- Тесты по умолчанию поднимают встроенный PostgreSQL 16 (pgserver); `KALYPSO_TEST_DSN`
  направляет их на внешний сервер (нужны права CREATEDB + CREATEROLE).
- Каждый тест получает свою БД-копию шаблона с применёнными миграциями.
- Новая миграция или ограничение — сразу тест в `tests/test_db_*.py`.
- Сервер: `docs/deploy.md`; зависимости сервера — `requirements.txt` (те же версии, что в pyproject).

## Окружение

- Python 3.12, PostgreSQL 16 (минимум 15 — нужен `NULLS NOT DISTINCT`).
- Интерфейс — русский, строки через слой локализации (готовность к казахскому).
