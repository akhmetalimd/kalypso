# KALYPSO — правила проекта

KALYPSO (KAzakhstan LYmphoma Patients Survival and Outcomes) — пробная платформа
регистра лимфопролиферативных заболеваний. Регистр — деперсонифицированный
исследовательский слой; his.kz — источник истины с персональными данными.
Между ними — граница деидентификации. Требования — PRD v1.0 (у владельца проекта).

## Непреложные правила

1. **Только синтетика.** В репозитории, тестах, фикстурах, логах и примерах — только
   синтетические данные. Реальные данные пациентов не загружаются до соглашения об
   обработке данных и одобрения этического комитета.
2. **ИИН не хранится и не логируется.** В БД попадает только `iin_hash` =
   HMAC-SHA256(ИИН, ключ) в полном виде (64 hex). Сырой ИИН живёт только в памяти
   запроса: не пишется в БД, логи, аудит, сообщения об ошибках, кэш, URL.
3. **Хэш считается только на сервере** (или в коннекторе his.kz внутри сети клиники).
   Ключ HMAC никогда не попадает в браузер, репозиторий или облако: у ИИН низкая
   энтропия, с ключом все хэши восстанавливаются перебором. Ключ — из окружения
   (`KALYPSO_HMAC_KEY`), один на все филиалы, смена ключа = новая `hash_key_version`.
4. **Деидентификация до AI.** Во внешнюю модель уходит только деидентифицированный
   текст. Свободный текст (гистология, ПЭТ-КТ) проверяется на идентификаторы перед
   сохранением; БД дополнительно отвергает 12-значные числа в этих полях.
5. **Человек в контуре.** AI создаёт только предложения. В регистр попадает лишь то,
   что принял или исправил куратор; провенанс записи это отражает.
6. **Без жёсткого удаления.** Клинические записи удаляются мягко (`deleted_at`);
   роль приложения не имеет DELETE на клинических таблицах.
7. **Два рубежа доступа.** Права проверяют сервисы (`config/roles.json`), и то же
   самое повторяет RLS в БД (миграция 0004). Новая клиническая таблица с `patient_id`
   получает такие же политики; функции, которым нужно видеть всё (проверки, дедупликация),
   — SECURITY DEFINER и отдают минимум.
8. **Аудит — на триггерах БД.** Приложение в каждой транзакции делает
   `SET LOCAL app.user_id = '<uuid>'` (и `app.change_reason` при пересмотре диагноза).
   `audit_log` и `diagnosis_version` неизменяемы.

## AI-ассист (П2)

- Конвейер: документ (`source_document`, только очищенный `kalypso/deid_text.py` текст +
  подтверждение пользователя) -> `kalypso/ai/pipeline.py` (служебный пользователь `ai-worker`)
  -> `ai_run` + `ai_proposal` -> сверка куратором (`kalypso/review.py`) -> запись в регистр с
  `source = 'ai_document'`, `source_record_id` = id предложения.
- Шлюз — куратор: право `review.apply`; RLS пускает его писать только строки `ai_document`,
  а в карточке пациента — только диагноз, текст гистологии, последний контакт (триггер
  `patient_curator_guard`). **Пакетного принятия нет** — каждое предложение решается отдельно.
- Извлекатели за интерфейсом `kalypso/ai/base.Extractor`: `rules` (без сети), `claude`
  (Anthropic API: JSON-схема, кэш системной части, `fallbacks: "default"`), `fake` (тесты).
  Модель в защищённом контуре — ещё одна реализация того же интерфейса.
- `KALYPSO_AI_EXTRACTOR` по умолчанию `off` (всё — в ручную очередь); в dev — `rules`.
- **Живые вызовы Claude — только с отдельного согласия владельца проекта на бюджет.**
  Тесты к сети не обращаются. `python -m kalypso.ai.evaluate --extractor claude --estimate` —
  смета без вызовов; живой прогон требует `--confirm-spend`.
- Любой сбой извлечения — документ в ручную очередь, конвейер не падает.

## Аналитика (П3)

- Конечные точки — `registry_core.endpoint` (OS, TTFT, PFS, mPFS, EFS, TTNT): определения в
  `registry_core.ENDPOINTS`; неточные даты — середина периода (`impute_date`); TTFT: смерть без
  лечения — цензура. События в день старта линии исходом линии не считаются.
- Каплан–Майер — `registry_core.km_estimate` (Гринвуд, ДИ log-log, ДИ медианы). Проверен на
  наборе Freireich 6-MP. **p-value, log-rank, Cox в платформе не считаются** — только на выгрузке.
- Группирующий маркер/анализ — только измеренный не позже 90 дней после начала отсчёта
  (`kalypso/analytics.py`), иначе «не определено на старте». Порог показателя — внешний.
- Графики — `kalypso/charts.py`, SVG на сервере; цвета только классами `.s1….s6` и переменными
  `--series-N` (палитра навыка dataviz, проверена валидатором на фонах карточек). У каждого
  графика — табличный двойник. Больше 6 серий — сворачивать в «прочие».
- Документы (FR-8) — `kalypso/docgen.py`, шаблоны из данных регистра, без AI, с пометкой «черновик».

## Приём из МИС (П4, задел под his.kz)

- Коннектор `python -m kalypso.ingest run --adapter …` — на сервере **в сети клиники**, служебный
  пользователь `his-connector` (роль `ingest_worker`). Он **только** раскладывает данные в
  `ingest_item`: в клинические таблицы не пишет и пациентов не видит (RLS).
- Адаптеры — `source_adapter.py` (`SourceAdapter`, `ManualAdapter` из файла, `HisKzAdapter` —
  заглушка до П5), синтетика — `kalypso/ingest/synthetic_his.py`. Любой новый адаптер обязан пройти
  `tests/test_adapters.py`.
- Маппинг — `config/field_mapping/his_kz.json` (данные, не код). **Белый список**: в регистр идут
  только описанные поля. ИИН -> HMAC; внешние ID записей МИС -> HMAC (`record_key`). Пути полей
  в конфиге — заглушки до спецификации поставщика (`docs/hiskz_integration_questions.md`).
- **Автоприменения нет**: всё структурное и документы применяет куратор (`kalypso/ingest/apply.py`,
  экран `/ingest`), с `source = 'his_structured'`. Элемент с проблемами маппинга можно только
  отклонить — правится конфиг, данные приходят следующим прогоном. Документ из МИС — после
  подтверждения куратором, что очищенный текст без идентификаторов.

## Схема данных

- `schema.sql` — нормативный baseline, **не редактируется**. Все изменения — новыми
  файлами в `db/migrations/` (порядковый номер + суть). Применение: `psql -1 -f <файл>`.
- В БД хранятся **коды**, а не русские подписи (`alive`, `death`, `M`…). Подписи на
  русском/казахском — в слое локализации. Названия систем и критериев (`Rai`, `Binet`,
  `iwCLL 2018`) остаются как есть.
- Провенанс у каждой записи: `source` (`his_structured` / `ai_document` / `manual`)
  + `provenance` (`retrospective` / `prospective`).
- Пропуск «условного» поля — код пропуска (`patient_missing`, `module_data.missing`),
  а не пустая ячейка.
- Нозологии — дерево WHO-HAEM5 в `config/nosology_tree.json`; модульные поля — EAV
  (`module_data`), без ALTER TABLE на каждую нозологию.

## Движок

- `registry_core.py` — без внешних зависимостей; логика, одинаковая на любой платформе.
  Самотест: `python registry_core.py`. Менять сигнатуры существующих функций нельзя,
  только добавлять новые.
- Log-rank и Cox в платформе не считаются — только на выгрузке (lifelines / R).
  Пороги для «Исследователя выживаемости» — внешние, не подбираются по этим же данным.

## Устройство (П1)

- `kalypso/deid.py` — проверка ИИН, HMAC, поиск идентификаторов в тексте.
- `kalypso/registry.py` — доменные сервисы: **единственный путь записи** в регистр
  (права, приведение ввода, проверки registry_core, одна транзакция, предупреждения QC).
- `kalypso/auth.py`, `kalypso/rbac.py` + `config/roles.json` — вход, сессии, CSRF, роли.
- `kalypso/admin.py`, `kalypso/export.py` — пользователи/филиалы/аудит/запросы, деидент. выгрузка.
- `kalypso/web/` — FastAPI + Jinja2, без JS. ИИН только в теле POST, в ответы не возвращается.
- `kalypso/locales/*.json` — подписи кодов (ru; kk — заготовка).
- `kalypso/migrate.py` — `schema.sql` + `db/migrations/*.sql`, учёт в `schema_migrations`.
- `kalypso/synthetic.py` — синтетическая когорта ХЛЛ через те же сервисы.

## Запуск и тесты

```bash
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements-dev.txt
.venv/Scripts/python -X utf8 -m kalypso.dev      # http://127.0.0.1:8765, учётки — kalypso/dev_seed.json
.venv/Scripts/python -X utf8 -m pytest
```

- `python -m kalypso.dev` поднимает встроенный PostgreSQL в `.devdb/`, применяет миграции и
  при пустой БД создаёт филиалы, пользователей и 60 синтетических пациентов.

- По умолчанию поднимается встроенный PostgreSQL 16 (pgserver); `KALYPSO_TEST_DSN`
  направляет тесты на внешний сервер (нужны права CREATEDB + CREATEROLE).
- Каждый тест получает свою БД-копию шаблона с применёнными миграциями.
- Новая миграция или ограничение — сразу тест в `tests/test_db_*.py`.

## Окружение

- Python 3.12, PostgreSQL 16 (минимум 15 — нужен `NULLS NOT DISTINCT`).
- Интерфейс — русский, строки через слой локализации (готовность к казахскому).
