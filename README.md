# KALYPSO — комплект для репродукции платформы регистра ЛПЗ

Это не готовый продукт, а **воспроизводимая основа** будущей платформы на
деперсонифицированных данных. Комплект кодирует все решения, принятые при
проектировании регистра, в переносимую форму: схему данных, конфиги и движок.

## Что внутри

| Файл | Что это |
|---|---|
| `schema.sql` | Схема БД (PostgreSQL): трёхуровневая модель пациент → линия → наблюдение, обязательное ядро (словарь v1.0), коды пропусков, провенанс, аудит, EAV для модулей, лабораторные с канонизацией, представление `v_survival`. |
| `config/nosology_tree.json` | Дерево WHO-HAEM5 = классификация и навигация. Узлы несут статус (active/coming_soon), модуль, коды (ICD-O, МКБ), стадирование, индекс, критерии ответа, маркеры. Добавить нозологию = добавить/активировать узел. |
| `config/lab_units.json` | Канонизация лабораторных единиц: LOINC → каноническая единица + коэффициенты перевода. Перевод задан **по показателю** (масса↔моль — свой коэффициент). Добавить показатель = одна запись. |
| `registry_core.py` | Движок без зависимостей: `canonicalize_lab`, `kaplan_meier`, `survival_by_threshold`, `validate_record`, `find_node`. Логика, которая должна быть одинаковой на любой платформе. Есть самотест (`python registry_core.py`). |
| `app.py` | Референс-API (FastAPI): ingest пациентов/лабораторных, автоканонизация, контроль качества, «Исследователь выживаемости». Тонкая обёртка над движком. Устарел относительно миграции 0002 (SQLite, старые ключи) — образец, не рабочий API. |
| `db/migrations/0002_p1_core.sql` | Миграция П1 поверх `schema.sql`: суррогатный PK + полный `iin_hash`, версии диагноза, связь наблюдение→линия, провенанс на каждой записи, коды вместо русских значений, аудит на триггерах, пользователи/роли/филиалы, мягкое удаление. |
| `CLAUDE.md` | Правила проекта: синтетика, ИИН не хранится, деидентификация до AI, человек в контуре. |
| `kalypso/` | Платформа П1: вход и роли, ручной ввод ХЛЛ, карточка с полнотой и QC, запросы межфилиального доступа, аудит, деидентифицированная выгрузка. Запуск на синтетике: `python -m kalypso.dev`. |

## Принципы, зашитые в код

- **Расширяемость** — дерево нозологий и config-таблица показателей: расширение = запись в конфиге, без изменения схемы (для модулей — EAV-таблица `module_data`).
- **Амбиспективность** — коды пропусков (`patient_missing`) и `provenance` на каждой записи; исходные лабораторные значения не затираются (`value_raw` + `value_canonical`).
- **Сопоставимость** — единый `patient_id` (хэш ИИН) для автодедупликации; каноническая единица на показатель; каноническая шкала коморбидности (CIRS).
- **Гранулярность события** — `event_type` включает «старт новой линии» и `death_cause`, чтобы собирать PFS / modified PFS / EFS / TTNT как запрос, а не как поле.

## Как запустить движок (без БД)

```bash
python platform/registry_core.py       # самотест: канонизация, KM, валидаторы
```

## Как поднять референс-API

`schema.sql` рассчитан на PostgreSQL (рекомендуется как целевая СУБД).
Для быстрой демонстрации на SQLite адаптируйте типы (ENUM → TEXT+CHECK уже готово;
JSONB → TEXT, `gen_random_uuid()` → генерация UUID в приложении, `TIMESTAMPTZ` → TEXT).

```bash
pip install fastapi uvicorn
uvicorn app:app --reload
# POST /patients, POST /labs (автоканонизация), GET /survival?analyte_loinc=..&threshold=..
```

## Граница ответственности (честно)

Комплект намеренно **не** включает аутентификацию, роли, разграничение доступа и
UI аудита — это слой развёртывания. Два пути:

- **REDCap** — если не хотите держать разработку: модель переносится в инструмент
  REDCap (data dictionary CSV из словаря ядра), роли/аудит/экспорт — из коробки.
  `nosology_tree.json` и `lab_units.json` подключаются как справочники/логика вычисляемых полей.
- **Собственная платформа** — `schema.sql` + `registry_core.py` как ядро, поверх —
  фреймворк с аутентификацией (роли: врач/куратор/аналитик), аудит на триггерах БД,
  и слой ПДн (хэширование ИИН выполняется до попадания на сервер).

## Совместимость с OMOP

Для внешних коллабораций и пулинга (как в HARMONY) ядро маппится на OMOP CDM:
`patient` → PERSON/OBSERVATION_PERIOD; `who_haem5`/`icd_o_3_2` → CONDITION_OCCURRENCE
(через словари SNOMED/ICD-O); `lab` → MEASUREMENT (LOINC + UCUM уже готовы);
`therapy_line` → DRUG_ERA/DRUG_EXPOSURE. Канонические единицы и LOINC делают этот
маппинг механическим.

## Статистика

`registry_core` даёт Каплан–Майер и медианы (для дашборда/песочницы). **Log-rank и
регрессия Кокса — на выгрузке** (lifelines / R): наблюдательные ассоциации требуют
поправки на риск и внешнего порога, а не подгонки по своим же данным.
